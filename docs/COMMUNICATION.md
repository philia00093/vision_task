# 通讯报告（树莓派 ⇄ 笔记本）

> 采集时间：2026-10-24 09:00 左右，热点 `Xiaomi 15 Pro`（2.4GHz，信道 11）
> 笔记本 `10.105.58.158` ⇄ 树莓派 `10.105.58.57`

## 1. 链路拓扑

```
树莓派                        笔记本
------                        ----------------
相机 2560×960 MJPG
  └ 右目 1280×960
      └ 裁剪 900×340 ──JPEG q80 (~29 KB)──▶  HTTP/1.1 POST /detect
                                             （application/octet-stream）
                                             24 条长连接，TCP_NODELAY
                                             服务端 MODEL_LOCK 串行推理
                                             640→960 imgsz，GPU
                       ◀──160 B 结果帧（含 ACK）──
      └ 解码/绘制 → /dev/fb0（1024×600）
```

- **握手**：启动 `GET /health` → 返回 `names`（类别）、`window`（窗口）、`ack: true`
- **上行**：二进制图像帧（16 B 帧头 + 12 B 元信息 + JPEG + 4 B CRC32）
- **下行**：恒定 160 B 结果帧（4 个检测槽 + 手部槽 + 步数 + 3 布尔 + **ACK 字段** + CRC32）

## 2. 帧格式

### 通用帧头（16 B，小端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | magic | `"VP"` |
| 2 | 1 | version | 1 |
| 3 | 1 | type | 1=图像 2=结果 3=ACK 0x7F=错误 |
| 4 | 1 | flags | 保留 |
| 5 | 1 | rsv8 | 0 |
| 6 | 2 | rsv16 | 0 |
| 8 | 4 | seq | 发送方自增 |
| 12 | 4 | payload_len | 载荷长度 |
| — | 4 | CRC32 | 覆盖帧头到载荷结尾 |

### 上行图像帧（type=1）

```
载荷 = 宽(u16) 高(u16) 格式(u8,1=JPEG) 质量(u8) rsv(u16) 时间戳(u32) + JPEG 原始字节
整帧 = 16 + 12 + JPEG + 4
```

### 下行结果帧（type=2，恒定 160 B）

| 偏移 | 长度 | 字段 | 顺序含义 |
|---|---|---|---|
| 0 | 4 | **ref_seq** | 这是第几帧图像的结果 —— **排序依据** |
| 4 | 1 | det_count | 有效检测数 0~4 |
| 5 | 3 | rsv | |
| 8 | 4 | cost_us | 推理耗时（微秒） |
| 12 | 80 | det[4] | 每槽 20 B：cls/valid/conf(千分比)/4 个点 |
| 92 | 20 | hand | 手部槽（预留） |
| 112 | 4 | step | 装配步数 + 3 rsv |
| 116 | 8 | flags | 3 个布尔 + 5 rsv |
| **124** | **4** | **ack_seq** | 服务端已处理完的帧号（确认） |
| **128** | **4** | **rcv_nxt** | 连续收到的最高帧号（累积确认） |
| **132** | **2** | **win** | 服务端剩余窗口 |
| 134 | 6 | rsv | |

### ACK 帧（type=3，32 B）

`ack_seq(u32) + rcv_nxt(u32) + win(u16) + rsv`，握手/单独确认用。

## 3. 流控机制

| 机制 | 实现 | 作用 |
|---|---|---|
| 滑动窗口 | 24 条长连接并发，服务端 `/health` 公布窗口 | 吞吐 ≈ 窗口 / RTT |
| 环形缓冲（发送侧） | `deque(maxlen=window*2)`，满了丢最旧 | 不无限堆积 |
| 背压 | 在飞 ≥ 窗口时直接丢帧（计入 dropped） | 防止 RTT 从 80ms 涨到 900ms |
| 顺序保护 | 只接受 `ref_seq >= 已收到最大值` 的结果 | 乱序结果不覆盖新结果 |
| 环形缓冲（显示侧） | 60 帧 / 4 秒，按 `ref_seq` 精确取帧，取不到就取"不超过它的最近一帧" | 画面与框严格对齐 |
| 预充 | 首次攒够 10 帧才出图（一次性） | 开局不抖 |
| 显示单调 | `display_seq` 只许前进，回退时保持上一帧 | 不跳回旧帧 |

## 5. 延迟预算

```
画面滞后 ≈ 上传时间(U) + 服务端排队(W × 推理) + 推理 + 下行 + 树莓派绘制
```

实测拆解（窗口 24、推理 6 ms 时）：

| 段 | 估算 | 说明 |
|---|---|---|
| 上传 | 30~50 ms | 29 KB @ 7 Mbit/s，不含重传 |
| 服务端排队 | **0~150 ms** | MODEL_LOCK 串行；最多 24 个请求排队 |
| 推理 | 6 ms（尖峰 50 ms） | |
| 下行 | <1 ms | 160 B |
| 树莓派绘制 | 5~8 ms | 缩放 + RGB565 + 写 fb |

**结论：RTT 的主要波动来自 Wi-Fi 抖动，其次才是服务端排队。**
窗口是双刃剑：`吞吐 ≈ W / RTT`，但 `排队 ≈ W × 推理`，W 越大延迟越高。

经验取值：`W ≈ 目标帧率 × RTT`，例如 30 fps × 0.15 s ≈ 4.5，实际取 8~24 之间；
观察 `迟到` 和 `画面滞后` 两个数来收敛。

## 6. 已知问题

| 问题 | 说明 | 建议 |
|---|---|---|
| 链路抖动大 | ping 18~250 ms，RTT 106~614 ms | 换 5GHz 热点 / 靠近路由器 / 有线 |
| 推理偶发尖峰 | 6 ms → 51 ms | 检查 GPU 占用、散热、其他进程 |
| 迟到帧多 | 窗口 24 时数百 | 减小窗口，或接受（只是浪费服务端算力） |
| 树莓派掉线 | 半小时 4~5 次 | 换 5V/3A 电源（屏幕曾报 undervoltage） |
